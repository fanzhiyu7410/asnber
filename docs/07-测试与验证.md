# 测试与验证策略

## 1. 目标

证明三件事：

1. **正确性**：BER/DER 的结构解析、DER 编码与 C ABI 行为符合规范与文档。
2. **鲁棒性**：任意输入不崩溃、不泄漏、不越界、不无限递归，失败时干净返回。
3. **兼容性**：与主流实现的编码结果、解码结构一致；ABI 在版本演进中保持向后兼容。

## 3. 单元测试框架：doctest

已确认选型：**doctest**（单头文件、轻量、无外部依赖、支持无异常配置）。

- 版本固定，编码阶段 vendored 到 `tests/third_party/doctest/`，避免 CI 网络依赖；当前仓库尚无该源码，清单中登记为计划引入。
- 测试目标同样以无异常配置为主；doctest 使用 `DOCTEST_CONFIG_NO_EXCEPTIONS`。只有框架无法支持时才允许在测试目标局部放开异常/RTTI，且不得传播到库目标。
- 测试按模块组织：

```text
tests/
├─ unit/       标签、长度、节点、值读取、错误、内存
├─ c_api/      C 语言 ABI 测试
├─ asnberc/      工具端到端（生成描述表 → 加载 → 解码/编码）
├─ pkix/       模块端到端：真实证书字段访问、ANY 形态、安装后独立消费
├─ pkcs1/      asnber-pkcs1：PKCS#1 RSA 公私钥字段、builder 往返与负例
├─ pkcs8/      asnber-pkcs8：明文/加密私钥信息字段与负例
├─ pkcs10/     asnber-pkcs10：证书请求字段、版本、builder 与负例
├─ pkcs12/     asnber-pkcs12：PFX/AuthenticatedSafe/SafeContents/CertBag 遍历与负例
├─ pkcs/       门面版本符号（`asnber-pkcs`）
├─ cms/        模块端到端：CMS ContentInfo / SignedData / EnvelopedData 真实样本字段与负例
├─ conformance/ DER/BER 向量与差分数据
├─ fuzz/       libFuzzer harness
├─ differential/ 差分工具（`asnber_dump`）与 `diff_asnber.py`（OpenSSL `asn1parse` / asn1tools）
├─ embedded/   静态池最小用例（宿主注册 CTest，交叉编译只构建）
├─ bench/      可选模块 open/close 基线（`ASNBER_BUILD_BENCHMARKS=ON`，不进 CTest）
└─ support/    测试向量加载、临时分配器、断言辅助
```

- 当前实际目录即上述十二项（`tests/smoke/` 已并入 `unit/` 并删除）。除 `bench/` 与 `differential/` 辅助目标外，每个目录至少注册一个 CTest 用例，使用无第三方依赖的最小 C 程序与 `tests/support/check.h` 断言；doctest 与 libFuzzer 在登记后接入。
- CTest 注册每个测试可执行文件；失败输出包含输入文件名、偏移与错误码。
- 测试不依赖当前工作目录；向量路径由 CMake 以编译定义传入。
- `test_asnberc_cli` 覆盖 CLI 契约：两次运行逐字节一致、C 数组与 `.bin` 一致、既有负例，以及多模块 `IMPORTS` 正/负例。`tests/data/asnberc/multimodule/golden.bin` 由该用例每次从同一组模块重新生成并逐字节比对，同时与人工展平输入（`flattened.asn1`）的输出比对；差异即失败，不保留一次性生成物。
- `test_pkix_cert_trim`：cert-decode 宿主行为断言与最小静态池测量；交叉构建
  只链接。`test_trim_symbols` 调用 `scripts/check_trim_symbols.py` 校验禁止/
  必须符号清单；`scripts/check_trim_config.py` 覆盖 8 条配置失败规则。
- `test_cert_csr`：cert-and-csr 上证书打开、证书编码、CSR 编码与 CSR 读回，并测量最小静态池。`test_cert_csr_symbols` 用 `scripts/check_trim_symbols.py --profile cert-and-csr` 确认编解码符号在、schema 运行时注册符号不在。

### 3.1 测试依赖的许可约束

- 测试与工具依赖仅接受 MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0（含 LLVM 例外）等宽松许可；禁止 GPL/LGPL/AGPL 或许可不明代码。
- doctest（MIT）为测试框架；libFuzzer（Apache-2.0 WITH LLVM-exception）随编译器工具链提供，不进入仓库、不随产物分发。
- 任一新增测试或 fuzz 依赖必须先登记到[第三方依赖与许可证清单](第三方依赖与许可证清单.md)，再进入代码。
- CI 检查点：`deps-license` job 运行 `python scripts/check_third_party.py`；发现未登记引用、禁止许可或清单格式错误即失败。
- OpenSSL `asn1parse`、Python `asn1tools` 属于 CI 外部参照，不链接、不分发，不计入依赖登记。

## 4. 一致性验证

### 4.1 规范向量

- 覆盖 BER 确定/不定长、DER 最短形式、高标签号、SET/SET OF 排序、BOOLEAN 规范值、OID 弧编码、字符串类型、边界长度（127/128/255/256/65535）。
- 覆盖错误向量：截断、长度溢出、EOC 缺失、DER 不定长、非最短长度、尾随字节、非法 BOOLEAN。
- 向量以“输入字节 + 期望结构 + 期望错误码”形式保存；期望值不依赖库自身实现生成。

### 4.2 差分与互操作

- **OpenSSL**：使用 `openssl asn1parse -inform DER/BER` 解析同一输入，比对标签层级、内容长度与偏移。仅作为外部参照，不作为运行时依赖。
- **Python asn1tools**：对公开模式生成 DER 向量，验证库对通用 DOM 的读取；模式相关语义不在基线比对范围。
- **往返不变性**：对合法 DER 输入，`decode → encode` 输出应与输入字节完全相同（规范 DER）；不等时记录差异并归类为解码宽松或编码规范化问题。
- **逐样本留档**：差分脚本可用 `--report` 与 `--report-json` 输出每个样本的逐条对照记录（样本名、双方偏移/层级/TLV 头长/内容长/形态、结论与往返结果）。Markdown 版本检入 `tests/differential/differential-report.md`，JSON 与之同目录；记录不含工具版本与时间戳，本地复跑可重现同一份文件。样本清单覆盖 PKIX 证书、PKCS#8/#1/#10 与 CMS ContentInfo/SignedData（attached、detached、无证书、多证书、subjectKeyIdentifier sid）、CMS EnvelopedData（ktri、多收件人 ktri、kari、kekri、pwri）以及 CMS EncryptedData（version 0，openssl `-EncryptedData_encrypt` 真实产物）。
- 差分测试不进入默认构建；`ci` 的 baseline 在打开 `ASNBER_BUILD_DIFFERENTIAL` 后执行对照。

## 5. 模糊测试

libFuzzer harness（一期起）：

| Harness | 输入 | 断言 |
| --- | --- | --- |
| `fuzz_decode_der` | 任意字节，DER 严格模式（覆盖 `NON_CANONICAL` 分支） | 不崩溃、不泄漏；成功则树结构自洽 |
| `fuzz_decode_ber` | 任意字节，BER 模式（含不定长） | 同上；深度/节点预算生效 |
| `fuzz_reader` | 任意字节分块喂给 reader（buffer + `_with_schema` 两路径） | 与 buffer 解码结果等价或同样失败 |
| `fuzz_schema_decode` | 任意字节 + 固定 schema（PKIX 表 + 覆盖各 kind/约束的小表，均与解码上下文同源） | 成功解码的树自洽；未知字段保留/`STRICT` 报错、ANY 三形态、EXPLICIT/IMPLICIT 剥壳、约束通过/失败均不崩溃 |
| `fuzz_roundtrip` | 任意 DER 成功样本 | 编码后再解码成功；结果与输入 DER 一致 |
| `fuzz_schema_load` | 任意字节作为描述表（二进制表加载） | 不崩溃、不泄漏；非法表返回错误码 |
| `fuzz_asnberc` | 任意字节作为 `.asn1` 文本（词法/语法入口） | 不崩溃、不死循环、诊断不泄漏 |
| `fuzz_pkix_open` | 任意字节作为 X.509 证书；open + 全部只读访问器 + `find` 路径 | 不崩溃、不泄漏；下标 0/count/SIZE_MAX 与 NULL 输出安全 |
| `fuzz_pkcs_open` | 经 `asnber-pkcs` 门面，任意字节依次按 PKCS#1/#8/#10 与 PKCS#12 各结构 open + 访问器，并按 contentType/bagId 继续解析嵌套结构 | 同上 |
| `fuzz_cms_open` | 任意字节按 ContentInfo open，再以 content 依次尝试 SignedData 与 EnvelopedData + 全部只读访问器；同一输入另驱动 builder 单 TLV 入口与 signer 路径并尝试编码 | 同上；写路径不崩溃、不泄漏 |

- 每个 harness 设置内存上限与超时（`-timeout -rss_limit_mb`）；OOM 视为失败。
- 崩溃样本进入 `tests/fuzz/corpus` 或 `tests/fuzz/regressions/` 并纳入常规 CTest（`test_fuzz_smoke` 冒烟）。
- 种子语料按 harness 分目录检入 `tests/fuzz/corpus/<harness>/`，由 `scripts/gen_fuzz_corpus.py` 确定性生成，扩展方式见 `tests/fuzz/README.md`。`schema_load` 语料包含真实 PKIX、PKCS#1/#8/#10/#12 与 CMS 描述表字节（0.4.0 起每个 ASN.1 文件一张表）；`decode_der` / `decode_ber` / `reader` / `schema_decode` / `roundtrip` 的 DER 种子包含 CMS ContentInfo/SignedData/EnvelopedData/EncryptedData 样本。模块 harness 的 `pkix_open` / `pkcs_open` / `cms_open` 语料只放对应结构的真实样本（`pkcs_open` 含 PFX 明文/加密/仅证书三份样本，`cms_open` 含 5 份 SignedData、6 份 EnvelopedData 与 1 份 EncryptedData 样本），并为每份样本派生截断、首字节标签翻转、长度字段 +1 三类变体。
- 本地实测（WSL2 Clang 21.1.8，ASan+UBSan+LSan）：10 个 harness 各短跑 60 s 无崩溃/泄漏/超时；长跑 `fuzz_schema_load` 900 s 亦无发现。新增的 `fuzz_pkix_open` / `fuzz_pkcs_open` / `fuzz_cms_open` 已在 Windows Clang 21.1.0（ASan+UBSan）与 WSL2 Clang 21.1.8（ASan+UBSan+LSan）各跑 60 s，退出码 0；Windows 平台 ASan 不支持 LSan，泄漏检测以 Linux 结果为准。CI 短预算 fuzz job 已把新增 harness 加入 `fuzz.yml` 矩阵。PKCS#12 节点把 `fuzz_pkcs_open` 扩展到 PFX/AuthenticatedSafe/SafeContents/CertBag 及嵌套解析，并在 Windows Clang 21 + ASan/UBSan 下以扩展语料短跑 20 s：3,661 次执行、0 命中、退出码 0。CMS 写路径与 `AttributeCertificate` 分支合并后，`fuzz_cms_open` 在 Windows Clang 21 + ASan/UBSan 下以检入语料 `-runs=0` 起步：初始 `cov 3064 / ft 4746`；60 s 后 `cov 3205 / ft 5920`、8,871 次执行（145 exec/s）、新增 152 单元、0 命中、退出码 0；`-merge=1` 去重最小化后的检入语料基线为 `cov 3206 / ft 5935`。另用 `-fprofile-instr-generate -fcoverage-mapping` 构建做源码覆盖率：`tests/fuzz/fuzz_cms_open.c` 行 98.43% / 分支 71.05%，`scan_signed_data` 与证书（`certificate_at`、`subject`/`issuer`/`serial`）、signer 访问器分支均被执行，原始 SignedData 独立 open 分支由新增种子触达。0.2.0 第一块把 `EnvelopedData` 接入 harness 与语料后，同一构建（Windows Clang 21 + ASan/UBSan）以检入语料 `-runs=0` 基线 `cov 3238 / ft 6549`（114 单元）、`-runs=1000` 47 s 内 0 命中、退出码 0。单次迭代耗时主要在模块结构 `open` 的 schema 解码（ContentInfo 约 1.77 ms、SignedData 约 2.06 ms），ctx 创建约 2.4 µs、accessor 扫描约 37 µs，因此未精简扫描顺序。
- AFL++ 作为可替代驱动，不作为基线必选。

### 5.1 语料、覆盖率与差分复跑

语料为确定性生成，均可本地复跑：

```bash
python3 scripts/gen_fuzz_corpus.py           # 各 harness 种子语料
python3 scripts/gen_schema_load_corpus.py    # schema_load 校验分支语料（越界/重叠/重复名/CONSTRAINT/名称表/decimal/tagMode）
```

schema 加载行/分支覆盖率（Clang + llvm-cov）。注意 libFuzzer 输出的 `cov:` 是 trace-pc-guard 的**边（edge）计数**，不是 llvm-cov 的块/分支覆盖率，两者不可直接等同：

```bash
cmake -S . -B build-cov -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DASNBER_BUILD_TESTS=ON \
  -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_C_FLAGS="-fprofile-instr-generate -fcoverage-mapping" \
  -DCMAKE_CXX_FLAGS="-fprofile-instr-generate -fcoverage-mapping" \
  -DCMAKE_EXE_LINKER_FLAGS="-fprofile-instr-generate"
cmake --build build-cov --parallel

# 检入语料全量（-runs=0 只跑种子，不做随机变异）
LLVM_PROFILE_FILE=cov/corpus_%p.profraw \
  build-cov/tests/fuzz/fuzz_schema_load -runs=0 tests/fuzz/corpus/schema_load/
# 短 fuzz 合并（-max_total_time）
LLVM_PROFILE_FILE=cov/fuzz_%p.profraw \
  build-cov/tests/fuzz/fuzz_schema_load -max_total_time=30 tests/fuzz/corpus/schema_load/

llvm-profdata merge -sparse cov/*.profraw -o cov/merged.profdata
llvm-cov report build-cov/src/CMakeFiles/asnber_static.dir/schema/asnber_schema_table.cpp.o \
  -instr-profile=cov/merged.profdata
```

差分复跑（OpenSSL `asn1parse` 为外部参照，需本机已装 openssl；asn1tools 缺装时该段显式 skipped）：

重新生成后 `git diff --exit-code tests/differential/differential-report.md` 必须无输出；有漂移说明样本或解码行为变化，先归因再更新记录。

### 7.1 发版前本地预检（工具链门禁）

打 tag 之前必须先在**本机**跑一遍预检。CI 的角色是背书，不是第一次发现错误的地方：

```bash
python scripts/local_precheck.py          # 逐档构建 + ctest + 链接警告检查
python scripts/local_precheck.py --list   # 只看档位与各自覆盖的风险
```

退出码 `0` 表示可以打 tag；非零（`1` = 有档位失败，`2` = 有档位因缺工具链被跳过）时不得打 tag、不得推送。`--only <档位>` 只跑一档，用于迭代，不能代替完整预检。

| 档位 | 配置 | 要求 | 覆盖的风险 |
| --- | --- | --- | --- |
| `msvc-debug-static` | MSVC x64 / Debug / 静态 | 必跑 | MSVC 默认语言标准（C++14）、`/W4 /WX`、`_MSC_VER` 分支、静态库重复链接 |
| `msvc-release-shared` | MSVC x64 / Release / 共享 | 必跑 | 优化 + `NDEBUG`、DLL 导出/导入宏 |
| `wsl-debug-shared` | WSL Linux GCC / Debug / 共享 | 必跑 | ELF 链接、`__linux__`、共享库符号可见性 |
| `wsl-release-static` | WSL Linux GCC / Release / 静态 | 必跑 | 优化下的告警、静态归档链接顺序 |
| `mingw-release-static` | MinGW GCC / Release / 静态 | 必跑 | `_WIN32` 但不带 `_MSC_VER`、GNU 链接器与 MSVC 的差异 |
| 其余 Debug/Release × 共享/静态 组合 | 同上 | 可省 | 由 CI 全量覆盖；预检只取每类风险的代表，不重复跑四个象限 |

- 可省档位的唯一理由是本机时间成本，不是风险可忽略。涉及 `__APPLE__`/ld64 的改动本机没有 macOS，必须在提交说明里点明“该平台结论只能由 CI 给出”。
- 语言标准类改动（例如给 INTERFACE 目标补 `cxx_std_*`）必须覆盖 MSVC 那一档：MSVC 默认按 C++14 编译，GCC/Clang 的默认标准更高，只跑 GCC 会漏判。
- 预检输出里**不得出现链接警告**：脚本扫描 `ld: warning:`、`ignoring duplicate libraries` 与 `LNK####`，命中即判失败。重复库意味着同一个库经直接与传递两条路径进入链接行，属于要修在 CMake 里的问题，不能长期挂成噪声。
- 与既有内容门禁的关系：`scripts/refactor_baseline.py --strict`、`scripts/check_exports.py`、`scripts/count_assertions.py --check`、`scripts/check_file_size.py` 校验“内容对不对”（描述表、导出符号、断言计数、单文件行数）；本地预检矩阵校验“能不能在各编译器上编译并通过测试”。两类门禁都要过，打 tag 前缺一不可。

## 8. 一期验收标准

一期（BER/DER 解码、DER 编码、C ABI、运行时构树）结束必须满足：

1. 规范向量与错误向量全部通过；差分测试无未解释差异。
2. C ABI 测试用 C99 编译通过，覆盖创建/销毁、错误查询、缓冲区释放、空指针防御。
3. ASan/UBSan 下全部测试无错误；失败注入分配器无泄漏。
4. 至少一个解码 fuzz harness 连续运行 24 小时无崩溃（CI 可用累计替代）。
5. Windows MSVC、Linux GCC、macOS AppleClang 三平台构建与测试通过。
6. 公共头文件在 C99 与 C++17 下均可独立包含；无 C++ 符号泄漏。
7. 文档中承诺的错误码、资源上限、所有权规则均有对应测试。
8. runtime 构树可完成“创建文档 → 创建根/子节点 → 设置值 → 封存 → DER 编码”全流程。

### 9.3 覆盖率提升过程中修复的真实缺陷

- `expectedTag` 对 `SEQUENCE/SEQUENCE_OF`、`SET/SET_OF` 无条件返回通用 16/17，导致 IMPLICIT 覆盖的构造类型永远无法匹配标签；现区分“显式剥壳后回到通用标签”与“IMPLICIT 使用类型自身标签”。回归用例见 `tests/c_api/test_schema_decode.c` 第 10 节。

### 9.8 发布证据引用规则

仓库文档**不记录发布提交（tag commit）自身的 CI run 号**；CI 结论以 GitHub Actions 页面为准，既不进入仓库文档，也不进入 Release 正文（写法见[发版说明规范](12-发版说明规范.md)）。

原因：若仓库文档写入 tag commit 的 run 号，就需要为这次文档修改再提交、再推送，从而产生新的 run，形成“每发一版还要再发一个纯文档补丁”的循环（0.1.1 → 0.1.2 就是这样发生的）。

- **切片级 run** 可以留在本文件：必须同时写明对应的提交哈希，并注明它**不是 tag commit**（如 §9.7 的 `33340a0`）。
- 仓库文档只描述“该版本已发布、发布说明见 Release 页”，不复制 run ID。
- Release 正文按[发版说明规范](12-发版说明规范.md)编写：只面向使用者，写新增、变更、移除、修复、升级注意与已知边界；不写 run ID、job 数量、用例数、耗时等过程证据。CI 通过是发版的前提，不是发版的内容。（2026-11-09 修订，撤回“Release 正文必须包含四个 workflow 的 run ID、符号数、用例数与已知边界”的旧要求；`v0.2.0` 正文按旧规则写成，保持原样。）
