# 编码规范与工程约定

## 1. 语言方言（硬约束）

| 项 | 规定 |
| --- | --- |
| 内部语言 | C++17，基线只验收 17；可实验性使用 20，但不得引入 20 专属特性 |
| 公共头文件 | C99；可由 C 与 C++ 同时包含 |
| 异常 | **全面禁用**：`-fno-exceptions`；MSVC `/EHs-c-` + `_HAS_EXCEPTIONS=0` |
| RTTI | **全面禁用**：`-fno-rtti`；MSVC `/GR-` |
| 标准库 | 核心只用 `<cstdint>`、`<cstddef>`、`<cstring>`、`<cstdarg>` 等无异常/无分配的头；禁止 `std::string`、`std::vector`、`std::function`、`std::iostream` |
| 全局状态 | 禁止可变全局对象、单例、隐式缓存；只允许常量初始化表 |
| 错误传播 | 返回 `Status`/错误码；禁止异常、`errno` 主通道、静默吞错 |
| IO | 核心不直接读写文件/网络/终端；输入输出经 reader/writer 回调 |

标准库容器可能抛出 `bad_alloc`，因此核心容器必须自研（基于 arena 或固定容量缓冲）。测试与工具可以例外，但不得进入库目标。

## 2. 命名

| 类别 | 规则 | 示例 |
| --- | --- | --- |
| 内部命名空间 | 核心 `asnber`；模块 `asnber::<模块>`；模块内部构造支撑 `asnber::module_detail`（asnber-cms / pkix / pkcs1 / pkcs8 / pkcs10 共用） | `namespace asnber { ... }`、`namespace asnber::pkix { ... }` |
| 类/结构体 | `PascalCase` | `Context`、`Document`、`Node`、`Arena` |
| 函数/方法 | `lowerCamelCase` | `parseTag`、`decodeBuffer`、`appendChild` |
| 成员变量 | `m_` + `lowerCamelCase` | `m_root`、`m_arena` |
| 局部变量/参数 | `lowerCamelCase` | `maxDepth`、`nodeCount` |
| 常量 | `k` + `PascalCase` | `kMaxDepth`、`kDefaultNodeLimit` |
| 类型别名 | `PascalCase`，以 `using` 定义 | `using ByteSpan = ...` |
| 文件 | 小写下划线 | `ber_decoder.cpp`、`node_model.h` |
| 核心公共 C 符号 | `asnber_` 前缀 | `asnber_decode_buffer` |
| 模块公共 C 符号 | `asnber_<模块>_` 前缀 | `asnber_pkix_cert_get_subject` |
| 模块导出宏 | `ASNBER_<模块>_API` | `ASNBER_PKIX_API` |

模块目录与命名空间一一对应：`modules/pkix/` ↔ C 前缀 `asnber_pkix_` / `ASNBER_PKIX_` ↔ C++ 命名空间 `asnber::pkix`；`cms`、`pkcs` 同理。核心代码不得引用任何模块命名空间或模块头文件。

**显式例外**：`src/` 内部纯数据 POD 结构（如 `Node`、`Document` 及描述表内存布局）允许使用 `snake_case` 字段命名，以便与描述表字段和固定偏移布局一一对应；`m_` + `lowerCamelCase` 只约束 class 与带行为成员的 struct。公共 C ABI 结构仍遵守第 5 节的 C 命名与字段规则。

禁止：拼音命名、无意义缩写、与公共 C 符号重名的内部类、双下划线标识符。

## 3. 文件组织

- 核心一个目录一个主题：公共头文件只在 `include/asnber/`，内部头文件只在 `src/`。
- 标准模块放在 `modules/<模块>/`，公共头文件在 `modules/<模块>/include/asnber/<模块>/`，内部头文件在 `modules/<模块>/src/`；模块不得把头文件放进核心 `include/asnber/` 根层。
- 工具放在 `tools/<工具>/`，可以复用公共 ABI，但不得依赖库内部头文件。
- 内部头文件不得被公共头文件包含；公共头文件不得包含 `src/` 下任何文件；核心公共头文件不得包含模块头文件。
- 源文件与头文件同名成对；实现细节放 `.cpp` 的匿名命名空间或 `namespace asnber::detail`。
- 单个翻译单元的实现细节需要跨 `.cpp` 共享时，内部头放在同目录的 `detail/`，命名 `<子系统>_internal.h`（如 `src/schema/detail/schema_encode_internal.h`、`modules/cms/src/detail/cms_builder_internal.h`、`tools/asnberc/src/detail/parser_internal.h`）。
- `detail/` 内部头只能被同一子系统的 `.cpp` 包含；不得出现在公共头、其他子系统或测试中。共享函数放进该子系统的 `asnber::<子系统>_detail` 命名空间。
- `modules/common/src/detail/module_builder_support.h` 是**唯一跨模块例外**：它是各模块构造翻译单元共用的支撑头，命名空间为 `asnber::module_detail`，只依赖核心公共 ABI，不安装、不导出。仅允许模块编译单元（`modules/*/src/`）包含，不得进入公共头、核心或工具；它不实现 DER `SET`/`SET OF` 排序，排序由核心 schema 感知编码负责（[ADR-0014](adr/0014-模块共享构造支撑.md) 已恢复）。
- 只有一个 `.cpp` 使用的辅助函数放该文件的匿名命名空间，不要为了“结构整齐”上提成内部头。
- 测试共用辅助放 `tests/support/`：按用途分库（如 `asnber_test_compare`），经 `asnber_test_support` 传递，不在各用例里复制实现。
- 每个文件顶部必须有文件说明：职责、所属模块、依赖方向、线程/所有权假设。
- 每个类、结构体、成员、方法必须有注释；注释使用中文，公共头文件注释同时给出英文术语。

## 4. 文件内分区

为消除“数千行单文件”和零散方法，源文件按固定分区排列，使用统一分隔注释：

```cpp
// ============================================================================
// 文件说明
// ============================================================================
// 职责：...
// 依赖：...
// 约束：...

// ============================================================================
// 依赖与前置声明
// ============================================================================

// ============================================================================
// 类型定义
// ============================================================================

// ============================================================================
// 静态常量 / 内部辅助类型
// ============================================================================

// ============================================================================
// 构造与析构
// ============================================================================

// ============================================================================
// 公共接口
// ============================================================================

// ============================================================================
// 私有实现
// ============================================================================

// ============================================================================
// 文件内辅助函数
// ============================================================================
```

规则：

1. 分区顺序固定，空分区可以省略，但不得打乱顺序。
2. 公共接口按调用顺序或功能分组，组内保持声明顺序与实现顺序一致。
3. 文件内辅助函数必须 `static` 或放入匿名命名空间，不得导出。
4. 单个 `.cpp` 目标 600 行、硬上限 800 行（含该文件配套的内部头）；超过 600 行按职责拆分，超过 800 行 CI 直接失败。任何例外必须登记在 `scripts/file_size_allowlist.txt`，且该清单只允许删除条目，不允许新增。
5. 拆分按语义边界切分：公共入口、标签与长度、尺寸测量、写出、分发等各自成文件；不允许 `#include "xxx.cpp"` 式假拆分，也不允许把同一状态定义复制到多个翻译单元。
6. 小逻辑不抽函数，直接内联。只有满足下列之一才提取：跨翻译单元复用；被 ≥3 处调用；块体超过约 10 行且有明确语义名；或属于必须集中执行的不变式（错误码写入、TLV 边界检查）。单行赋值包装、只改参数名的转发、只调用一次的“helper”一律内联，删除时同步删掉其注释块。
7. 不允许跨分区前向引用造成阅读跳跃；必要时在“前置声明”区集中声明。

## 5. 头文件规范

内部头文件：

- 使用 include guard（项目统一风格），不使用 `#pragma once`，保证嵌入式旧工具链兼容。
- 只包含必要的头；能用前置声明就不包含定义。
- 禁止 `using namespace`；禁止在头文件定义非 `inline` 函数或对象。
- 所有函数标注 `noexcept`（因为异常已禁用，标注用于表达契约）。
- 成员按“类型、构造/析构、公共接口、私有数据”顺序排列；数据成员统一 `m_` 前缀。

公共 C 头文件：

- 只包含 C 标准头；`extern "C"` 包裹；核心导出符号带 `ASNBER_API`，模块导出符号带对应的 `ASNBER_<模块>_API`。
- 枚举显式赋值；结构体字段带注释与 `struct_size` 约定。
- 不暴露数组长度依赖、内部布局、宏技巧；不使用匿名 union/struct。
- 只增不改：已发布声明不得删除或改签名；新增字段放在预留区或新结构体。
- **禁止在源码中手写版本宏**：`ASNBER_VERSION_*` 与 `ASNBER_<模块>_VERSION_*` 只能来自 CMake 从 `project(... VERSION ...)` 生成的版本头；源码树中的头文件不得出现硬编码版本号。
- 模块头文件互相独立，核心伞头不得包含模块头；模块头也不得要求消费者包含核心未公开的符号。

## 6. 类型与内存

- 禁止裸 `new/delete`；所有对象通过上下文/arena 创建。
- 禁止 `reinterpret_cast` 规避类型系统；必要的 ABI 句柄转换使用 `static_cast` + 不透明指针封装。
- 禁止未初始化变量；结构体使用值初始化或显式清零。
- 位运算使用固定宽度类型；禁止对有符号数做位移与溢出依赖。
- 字符串与二进制一律使用“指针 + 长度”，禁止依赖 `'\0'` 结尾表示长度。
- 比较/长度计算注意 `size_t` 与有符号数混用；开启 `-Wconversion -Wsign-conversion` 并在代码中显式转换。

## 7. 错误与断言

- 每个可能失败的操作返回 `Status`；调用方必须处理或显式向上传播。
- `ASNBER_ASSERT` 只用于内部不变量，启用条件为调试构建；发布构建中不得依赖断言产生副作用。
- 禁止 `abort()`、`exit()`、向 `stderr` 打印；错误通过上下文报告。
- 失败路径先清理再返回；禁止 `goto` 跨初始化，必要时使用 RAII 的轻量清理器（不抛出）。

## 8. 注释与文档

- 每个公共 API 在头文件中说明：参数、返回值、所有权、线程约束、失败条件。
- 每个内部方法说明前置条件、后置条件与所有权；复杂算法说明不变量。
- 注释解释“为什么”，不复述代码“做什么”；错误码与偏移的单位必须写明。
- 文档与代码中的术语以[术语表](10-术语表.md)为准。

## 9. 格式与工具

- 缩进 4 空格，行宽 100；大括号采用 K&R（函数左括号换行由 `.clang-format` 固化）。
- `.clang-tidy` 已入库（clang-tidy 21.1 补充扫描，见 [测试与验证](07-测试与验证.md)）；`.clang-format` 尚未加入，格式以本节缩进/行宽规则为准。
- 提交前必须通过 `ASNBER_WARNINGS_AS_ERRORS=ON` 构建；不允许用局部 `#pragma` 静默告警，除非注释说明原因。
- 代码评审检查项：分区是否规范、注释是否完整、是否存在跨层依赖、是否引入异常/RTTI/全局状态、公共头文件是否只增不改。

## 10. 提交与变更

- 一个提交只做一件事；文档变更与实现变更分开提交。
- 按任务节点提交：覆盖率补齐、`asnber-cms` 模块、`asnber-pkcs` 模块等每个节点完成后各提交一次；提交前必须 `ctest` 全通过，不通过不提交。提交消息写清做了什么与为什么，不贴文件清单。
- 修改公共 ABI 必须附 ADR 与版本影响说明；修改错误码语义必须附迁移说明。
- 版本号变更只改对应 `project(... VERSION ...)`，不得同时修改生成头或包配置文件；生成物由构建系统产出。
- 不提交构建产物、IDE 工程文件、测试临时文件；`.gitignore` 为唯一忽略规则来源。
- **新增依赖须先登记**：任何第三方依赖（含测试框架、fuzz 驱动、工具库）必须先更新 [第三方依赖与许可证清单](第三方依赖与许可证清单.md)，说明版本、用途、许可证与是否随产物分发，并通过 `python scripts/check_third_party.py`；运行库不得引入第三方依赖。禁止 GPL/LGPL/AGPL 或许可不明代码。
