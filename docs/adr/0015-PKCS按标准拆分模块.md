# ADR-0015：PKCS 按标准拆分模块与共享库布局变更

- 状态：已确认（用户批准，2026-11-09）
- 日期：2026-11-09
- 关联：[ADR-0009](0009-分层与独立模块策略.md)、[ADR-0012](0012-标准模块路线与只读边界.md)、[ADR-0014](0014-模块共享构造支撑.md)

## 背景

0.3.0 的 `asnber-pkcs` 把 PKCS#1/#8/#10/#12 四类结构放在同一个包里：一个共享库、一套描述表、一份公共头。带来三个问题：

1. **裁切粒度不足**：只要用到 PKCS#8，就会连带链接 PKCS#1/#10/#12 的描述表与代码；静态链接只能按目标文件裁切，而四类结构共享同一个库，无法按标准取舍。
2. **依赖方向风险**：PKCS#12 的 `bagValue` 常被误当作“必须解析 PKCS#8”的入口，容易演化出 `asnber-pkcs → asnber-cms` 或包内反向依赖。
3. **发布边界模糊**：一个包同时承载四份标准与四组 ABI，版本与变更影响面被放大。

同时，0.4.0 需要在 CMS 侧提供 ContentInfo 写侧入口，供 PKCS#12 调用方在**不新增模块依赖**的前提下组装 `ContentInfo`。

## 决策

### 1. 按标准拆包

| 包 | 标准 | 符号数 | 依赖 |
| --- | --- | --- | --- |
| `asnber-pkcs1` | RFC 8017 附录 A | 15 | 仅核心 |
| `asnber-pkcs8` | RFC 5208 | 15 | 仅核心 |
| `asnber-pkcs10` | RFC 2986 | 14 | 仅核心 |
| `asnber-pkcs12` | RFC 7292 | 25 | 仅核心 |
| `asnber-pkcs` | 聚合包（不产库） | 0 | 核心 + 上述四包（INTERFACE） |

- 四个实现包互不依赖，也不依赖 `asnber-pkix` / `asnber-cms`。
- `asnber-pkcs` 不产库、不导符号（早期实现曾保留 `asnber_pkcs_version_string`，后续收掉）：`pkcs.h` 聚合四个实现包的公共头，`asnber::pkcs` 是 INTERFACE 目标，以依赖方式把四个包传递给使用者；`find_package(asnber-pkcs)` 用法不变，链接目标由 `asnber::pkcs::shared/static` 统一为 `asnber::pkcs`。
- 实现包的公共头前缀与 ABI 宏按包独立：`ASNBER_PKCS1_API` / `ASNBER_PKCS8_API` / `ASNBER_PKCS10_API` / `ASNBER_PKCS12_API`；符号名保持 `asnber_pkcs_*` / `asnber_pkcs12_*` 不变，避免调用方改代码。

### 2. 不建 `asnber-pkcs5`

PKCS#5 只定义口令派生与加密方案，本仓库未导出任何 PKCS#5 结构符号，也没有对应描述表。为“标准齐全”建一个零符号空模块只会增加安装体积与文档噪声，因此不建；将来若增加 PBKDF2/PBES2 参数结构访问，再按本 ADR 第 1 条的模式新开包。

### 3. PKCS#12 与 CMS 不建立依赖（已确认，禁止回退）

**决策：`asnber-pkcs12` 不建立对 `asnber-cms` 的依赖，保持独立。** 优先级是模块独立性：PKCS#12 的只读能力不需要 CMS 的 SignedData/EnvelopedData 等结构，引入依赖只会带来版本耦合与额外表体。

- PKCS#12 的 `content` / `bagValue` 一律按**完整原始 TLV** 暴露，由调用方决定是否交给 `asnber-pkcs8`、`asnber-pkix` 或应用自己的解析器。
- CMS 侧在 0.4.0 提供 ContentInfo 写侧 6 个 API（`asnber_cms_content_info_builder_*`，cms 142→148），调用方可以“用 PKCS#12 读取原始 TLV，再用 CMS builder 组装 ContentInfo”，这是**应用层组合**，不构成包依赖。
- 因此 `asnber-pkcs12` 的链接依赖只有核心；其 CMake 只链接 `asnber::shared` / `asnber::static`，安装配置只 `find_dependency(asnber)`。
- **维护约束**：后续不得以“复用 ContentInfo 实现”为由给 `asnber-pkcs12` 增加 `asnber-cms` 链接或 `find_dependency`。若业务确实需要 PKCS#12 写 PFX，由调用方同时链接两个包；确需改变本决策时必须新开 ADR 并说明 footprint 代价（`cms_content_info_schema` 19,040 B + 约 1.2–6.4 KB 代码）。

### 4. 一表一翻译单元

- 每张描述表对应一个 `.cpp` 访问器，数组在 C++ 中为内部链接；同一模块的多张表不合并进同一个翻译单元。
- 理由：静态链接按 `.o` 裁表的前提是“一张表一个目标文件”；合表会让“只用 PKCS#1 公钥”也不得不为私钥表付出体积。
- 生成头中的数组符号由模块名派生，同一模块多张表符号相同，必须靠“一表一 TU”避免冲突（0.4.0 起每模块只剩一张表，该约束自动满足）。

### 5. D5 已在 0.4.0 落地

“一文件一表 + 运行时指定根”已在 0.4.0 完成：

- **结果**：全仓描述表体 161,200 → 51,512 字节；同文件各表逐字节只差 CRC32C 与 `root_type_id`，合并后除根外等价。
- **核心入口**：新增 `asnber_schema_load_with_root`（ABI 68 → 69）。`root_type_id = 0` 沿用表头，非 0 覆盖且必须落在 `1..type_count`，越界返回 `ASNBER_E_INVALID_ARG`；表头自身的根仍按格式校验。
- **根登记**：模块私有常量记录原 `.bin` 偏移 96 的根编号，`scripts/refactor_baseline.py` 复核“表头默认根一致、登记根 ≤ type_count”，表结构漂移时失败。
- **生成期**：每个 ASN.1 文件只生成一张表，仍保持“一张表一个翻译单元”。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 继续单包，仅按源文件拆分 | 无法按标准裁切共享库；静态链接仍被单库绑定；发布影响面不变 |
| 拆包但保留 `asnber-pkcs` 导出全部符号 | 符号重复导出，两个共享库提供同一符号，调用方链接结果不确定；ABI 基线无法收敛 |
| `asnber-pkcs12` 依赖 `asnber-cms` 复用 ContentInfo | 引入模块间依赖，版本耦合；PKCS#12 只读语义并不需要 CMS 的 SignedData 等结构 |
| 建零符号 `asnber-pkcs5` 占位 | 只增加安装与文档负担，无实际可链接能力 |
| 多张表合并进同一翻译单元以减少文件数 | 破坏静态链接按 `.o` 裁表的能力，与本轮拆分收益直接冲突 |

## 后果

- ABI：`asnber-pkcs` 70→0（不产库、无基线文件，基线由 8 包降为 7 包）；新增 `asnber-pkcs1` 15、`asnber-pkcs8` 15、`asnber-pkcs10` 14；`asnber-pkcs12` 25 维持；`asnber-cms` 142→148（ContentInfo 写侧）。
- 安装：新增 `asnber-pkcs1/8/10/12` 四个 CMake 包；`asnber-pkcs` 的 Config 生成 `find_dependency(asnber-pkcs1/8/10/12)`，安装时必须同时安装四个实现包。
- 构建：新增 `ASNBER_BUILD_MODULE_PKCS1/8/10/12` 与 `ASNBER_PKCS1/8/10/12_REGENERATE_TABLE` 选项；`ASNBER_BUILD_MODULE_PKCS=ON` 时四个实现包必须同时启用（配置期校验）。
- 文档：`docs/01`、`docs/02`、`docs/02b`、`docs/03`、`docs/06`、`docs/07`、`docs/09`、`docs/10`、文档索引与基线覆盖度清单同步；`abi/README.md` 记录 0.4.0 基线。
- 依赖：`asnber-pkcs12` 的链接与安装配置都不含 `asnber-cms`（只 `find_dependency(asnber)`）；`tests/consumer/consumer_pkcs12.c` 只 `find_package(asnber-pkcs12)`，用于守住这一点。
- 测试：`tests/pkcs1/8/10` 各自只链接本包；聚合包保留版本宏与核心同源的测试；消费工程新增 `asnber-pkcs1` 与 `asnber-pkcs12`；fuzz 以聚合包转发的静态实现包覆盖全部 PKCS 结构。
- 后续：D5 已在 0.4.0 落地（见第 5 节）；新增密码学语义或 PKCS#5 结构访问须新开 ADR。
