# ADR-0012：标准模块路线、展平自包含策略与只读边界

- 状态：已确认（用户批准，2026-11-06）
- 日期：2026-11-06
- 关联：[ADR-0009](0009-分层与独立模块策略.md)、[ADR-0007](0007-模式层边界.md)、[能力范围](../03-ASN1能力范围.md)、[里程碑](../09-里程碑与分期.md)、[描述表格式](../11-描述表格式.md)

## 背景

ADR-0009 确定分层：核心零领域知识，`asnber-pkix`、`asnber-cms`、`asnber-pkcs` 为独立包，模块只依赖核心、模块之间不互相依赖。实际推进中还需要回答三个问题：

1. 三个标准模块按什么顺序做、每个模块做到什么粒度；
2. CMS 需要 PKIX 的 `AlgorithmIdentifier`、`Extension`、`Attribute` 等类型时，如何在不新增模块间依赖的前提下复用；
3. 第一版模块是否承担密码学语义（验签、解密、密钥运算）。

同时，ADR-0009 与 ADR-0007 中“一期必须支持 `IMPORTS` 与单参数参数化”的表述与已落地的展平输入路线冲突：`asnberc` 当时以自包含展平模块为输入，`IMPORTS` 与参数化只报诊断。需要一并收敛。（后续 A 阶段已支持多模块 `IMPORTS`，9007 移除，见第 5 节。）

## 决策

### 1. 路线顺序

1. `asnber-pkcs` 先做：PKCS#8 + PKCS#1，只读。
2. `asnber-cms` 后做。

### 2. 切片

| 顺序 | 内容 | 阶段 | 边界 |
| --- | --- | --- | --- |
| 1 | PKCS#1（RFC 8017）+ PKCS#8（RFC 5208 及相关勘误） | 已完成 | 只读结构 |
| 2 | PKCS#10（RFC 2986） | 已完成 | 只读结构 |
| 3 | PKCS#12（RFC 7292） | 已完成 | 只读结构 |
| — | PKCS#7 | 不单独做 | 归入 `asnber-cms` |

注（2026-11-11）：第 1–3 项均已交付；0.4.0 起按 [ADR-0015](0015-PKCS按标准拆分模块.md) 拆为 `asnber-pkcs1/8/10/12`，0.5.0 起各包在只读访问之外提供对应 builder（构造支撑见 [ADR-0014](0014-模块共享构造支撑.md)），仍不涉及密码学语义（第 4 节）。

### 3. 模块隔离与 CMS 的展平自包含

- ADR-0009 的“模块只依赖核心、模块之间不互相依赖”**保持不变**（0.4.0 起 `asnber-pkcs` 退化为门面包，只向下依赖四个实现包，见 [ADR-0015](0015-PKCS按标准拆分模块.md)）。
- `asnber-cms` 需要的 PKIX 类型，在 `asnber-cms` 自己的展平模块中**复制所需类型**（如 `AlgorithmIdentifier`、`Extension`、`Attribute`），不新增 `asnber-cms → asnber-pkix` 依赖。
- 代价：
  - CMS 描述表更大，同一类型在 pkix 与 cms 各有一份定义；
  - 类型级对账要按模块分别做，缺陷可能需要在两份定义中分别修复；
  - 产物体积与符号存在重复。
- 缓解：
  - 每个模块维护自包含展平文件与类型级对账表，逐类型对齐 RFC 原文；
  - 以 RFC 原文为唯一事实来源，不共享实现代码，只共享核心公共 ABI；
  - 复制范围限定为 CMS 结构实际引用的类型，不做整模块照搬。

### 4. 只读边界

第一版所有模块不做密码学语义的写；结构构造（按 RFC 组装与 DER 编码）不属于密码学语义，边界见第 6 节：

- `asnber-cms`：只读 `ContentInfo` / `SignedData` / `EnvelopedData` 结构；不验签、不摘要、不解密、不校验证书链。
- `asnber-pkcs` 的 PKCS#8：只读 `PrivateKeyInfo` / `EncryptedPrivateKeyInfo` 结构，不解密。
- `asnber-pkcs` 的 PKCS#1：只读 ASN.1 结构；不做 RSA 运算、填充、签名、加密；填充参数仅作为 `ANY` 保留。
- `ANY` 字段只返回原始 TLV，由调用方按 OID 二次解析。

### 5. 展平输入与工具边界

`asnberc` 初期输入是自包含展平模块；A 阶段起已支持多模块 `IMPORTS` 并合并为一张描述表（诊断映射见[描述表格式](../11-描述表格式.md)）：

- 多模块 `IMPORTS`/`EXPORTS` 已支持，导入失败按 9002/9003 诊断，不再有 9007；
- 参数化定义/实例化仍报 `ASNBERC_E_UNSUPPORTED_CONSTRUCT`(9006)；
- 参数化展开与直接消费原始 RFC 模块（`CLASS`/信息对象集）留后续，不阻塞本 ADR 的模块切片。

修订注记（0.1.0）：单类型参数化定义与实例化已支持（`Foo { Type } ::= ...` 与 `Foo { INTEGER }`），上一行“参数化定义/实例化仍报 9006”现仅对值参数与多参数成立；`CLASS`/信息对象集直接解析仍留后续。

### 6. 结构构造边界（补充，2026-11-07）

`asnber-cms` 在只读解析之外提供 `ContentInfo` / `SignedData` / `EnvelopedData` 的结构构造与 DER 编码，不改变第 4 节的密码学边界：

- builder 只用核心公共 ABI（含 `asnber_node_create_any`）与随包描述表，不新增编码器、不包含核心内部头；
- `CMSVersion`、算法 OID、eContent、签名值与证书/CRL 原始 DER 由调用方显式给值并原样承载，模块不推导、不校验业务范围；
- `signedAttrs` / `unsignedAttrs`（及 `unprotectedAttrs`）只改写外层标签（`0x31` → `0xA0` / `0xA1`），长度与内容逐字节不变，不重建、不排序；输入须为非空 `SET OF Attribute`（元素为 `SEQUENCE`），签名覆盖的是 `SET OF` 编码，调用方须对同一份字节签名；
- `certificates` / `crls` 校验单 TLV、分支根标签（`CertificateChoices` 的 SEQUENCE/[0..3] 与 `RevocationInfoChoice` 的 SEQUENCE/[1]）并按 DER `SET OF` 排序，不解析内部、不做信任判断；`sid` 的 issuer/serialNumber 只校验 `SEQUENCE`/`INTEGER` 根标签；
- 不生成签名、不计算摘要、不做加解密、不校验证书链；新增这些能力仍须新开 ADR。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| `asnber-cms` 链接并依赖 `asnber-pkix` 复用类型 | 引入模块间依赖，违反 ADR-0009；模块版本被迫耦合，安装依赖链变长，任一模块升级会牵动另一个 |
| 把 PKIX 公共类型下沉到核心 | 核心被证书领域概念污染，违背核心零领域知识原则 |
| CMS 与 PKIX 共用一个跨模块“公共类型包” | 实质仍是模块间依赖，且新增第四个包与版本矩阵，收益低于复制成本 |
| 第一版就提供解密/验签/密钥运算 | 引入密码学实现与安全边界，超出 ASN.1 库定位；错误更容易被误用为安全结论 |

## 后果

- `docs/03`、`docs/09`、`docs/01`、模块 README 必须同步本 ADR 的顺序、切片与只读边界。
- `asnber-pkcs` 第一切片交付 PKCS#8 + PKCS#1 只读结构访问；PKCS#10 已按第 2 项落地；PKCS#12 只读切片已于 2026-11-07 完成，PKCS#7 归 CMS。四类结构分别在 `asnber-pkcs1/8/10/12`，`asnber-pkcs` 仅作门面（见 [ADR-0015](0015-PKCS按标准拆分模块.md)）。
- CMS 实现时必须自带展平模块，并附类型级对账表；CI 需分别校验各模块的生成表。
- ADR-0009 决策 6、ADR-0007 决策 6 与 ADR-0008 D20 中“一期必须支持 `IMPORTS`/参数化”的表述由本 ADR 修订。
- 新增密码学语义能力必须新开 ADR，不得在模块内静默扩展。
