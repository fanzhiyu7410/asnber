# ADR-0010：版本一致性机制

- 状态：已确认（用户批准，2026-11-03）
- 日期：2026-11-03
- 关联：[ADR-0001](0001-C-ABI边界.md)、[ADR-0008](0008-基线决策汇总.md)（D18）、[C API 第 6.4 与 11 节](../02-C-API规范.md#64-版本查询与自检)、[构建与移植第 8 节](../06-构建与移植.md#8-版本与-abi-产物)

## 背景

版本号原本可能同时出现在 CMake 项目定义、公共头文件宏与运行时字符串中。多包布局下，核心 `asnber` 与 `asnber-pkix`、`asnber-cms`、`asnber-pkcs` 各自需要一套版本；任何一处手写都可能在发版时漂移，使调用方误判 ABI 兼容性，直接违背 D7 的向后兼容承诺。

## 决策

1. **唯一来源**：核心以根 `CMakeLists.txt` 的 `project(asnber VERSION x.y.z)` 为真源；每个模块以自己 `project(... VERSION ...)` 为真源，互不覆盖。
2. **生成版本头**：用 `configure_file(@ONLY)` 从 `cmake/asnber_version.h.in` 与 `cmake/asnberModuleVersion.h.in` 生成 `<包>_version.h`，含 `MAJOR/MINOR/PATCH/STRING/ENCODED`；输出到构建目录，以 `target_include_directories` 暴露并随安装发布。源码树中不手写版本宏。
3. **运行时查询**：核心提供 `asnber_version()`，填充带 `struct_size` 的 `asnber_version_info_t`（含 `capabilities` 能力位），返回**实际链接的库版本**。编译期宏代表调用方编译时版本，两者允许因头文件与二进制不同而分离。
4. **运行时自检**：`asnber_version_check(expected_major, expected_minor)` 只对**主版本不一致**返回 `ASNBER_E_VERSION_MISMATCH`；次版本差异视为兼容，`expected_minor` 仅用于诊断与未来策略。供宿主初始化自检，典型场景是“旧头新库/新头旧库”，检测方式见 C API 规范第 6.4 节。可选能力通过 `capabilities` 与 `asnber_has_capability()` 查询。
5. **产物名与 SONAME**：共享库文件名与 `SOVERSION` 从 `project VERSION` 派生；`VERSION` 为完整版本，`SOVERSION` 为主版本。规则见构建与移植第 8.3 节。
6. **包配置**：各包用 `write_basic_package_version_file` 生成 `<包>ConfigVersion.cmake`；模块通过 `find_dependency(asnber <最低版本> CONFIG)` 声明所需核心的最低版本。
7. **CI 断言**：构建期/CI 校验生成头、SONAME、包配置版本三者与 `project VERSION` 一致，不一致即失败。

## 备选方案

- **A 手写版本头 + CI 比对**：实现简单，但版本号存在两处来源，发版时容易漏改；CI 只能事后发现，不能消除漂移根源。
- **C 只保留运行时版本、不设宏**：宏消失后调用方无法在编译期做条件编译与版本分支，兼容性检查能力变弱。

两者均被否决。选 B（CMake 生成版本头）在保持单一来源的同时保留编译期与运行时两套检查能力。

## 后果

- 新增 `cmake/AsnberVersion.cmake` 与两个模板；核心与三个模块的 `CMakeLists.txt` 接入生成与安装。
- `include/asnber/asnber.h` 与各模块伞头包含对应生成版本头；消费者只需包含公共头即可获得版本宏。
- 版本变更流程收敛为“只改 `project(... VERSION ...)`”；生成头、SONAME 与包版本文件由构建系统同步产出。
- 公共头文件仍遵守只增不改；若未来需要扩展版本结构体，沿用 `struct_size` 尾部追加规则。
- 实现阶段若发现机制不可行，必须先新增 ADR 取代本条，再改代码。
