# ADR-0011：第三方依赖与许可证策略

- 状态：已确认（用户批准，2026-11-03）
- 日期：2026-11-03
- 关联：[ADR-0008](0008-基线决策汇总.md)（D9、D19）、[第三方依赖与许可证清单](../第三方依赖与许可证清单.md)、[构建与移植第 9 节](../06-构建与移植.md#9-第三方依赖与许可证)、[测试与验证](../07-测试与验证.md)、[编码规范](../08-编码规范.md)

## 背景

项目以 MIT 发布，需要同时保证两件事：运行库不把第三方许可证义务带给集成方；测试与工具引入的依赖可审计、可替换。此前只约定 doctest 为 MIT，缺少统一的登记表、许可范围与自动检查，容易在编码阶段随意引入依赖，导致后期替换或补授权成本上升。

## 决策

1. **运行库零第三方依赖**：核心 `asnber` 与三个模块的发版产物（shared/static）不得链接任何第三方库，仅允许 C 运行库与平台系统库。
2. **测试与工具依赖限定宽松许可**：仅接受 MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0（含 LLVM 例外）等宽松许可；禁止 GPL/LGPL/AGPL 或许可不明代码进入仓库。
3. **依赖登记**：`docs/第三方依赖与许可证清单.md` 为唯一登记入口，逐项记录名称、版本、用途、引入阶段、许可证、来源链接、是否随产物分发。
4. **构建期与 CI 检查**：提供 `scripts/check_third_party.py`，比对清单与实际引用，发现未登记依赖即失败；一期 CI 接入时挂为独立 job。
5. **分发合规**：`LICENSE` 维持 MIT；发版随包提供 `THIRD_PARTY_NOTICES.md`（当前无随产物分发的第三方组件，保持空模板）；README 增加依赖声明。
6. **变更流程**：任何新增依赖必须先更新清单并说明许可证，再进入代码；评审同时检查清单、分发声明与实际引用。

## 当前实际状态

- 仓库内尚无第三方源码；doctest 尚未 vendored，登记为计划引入的测试框架。
- libFuzzer 随编译器工具链提供，不进入仓库、不随产物分发。
- OpenSSL `asn1parse`、Python `asn1tools` 仅作为 CI 差分测试的外部参照，不链接、不分发，不计入依赖登记。

## 备选方案

- **A 只允许 doctest，工具与运行库零第三方**：约束最强，但 `asnberc` 若需要语法解析辅助库会被直接排除，扩展成本高。
- **C 不限制依赖，仅记录**：短期最快，但 GPL/LGPL 或许可不明代码可能进入仓库，MIT 发布与商业集成面临法律风险。

采用“运行库零第三方 + 测试/工具宽松许可白名单 + 逐项登记 + CI 检查”，兼顾合规与工具实现空间。

## 后果

- 新增 `docs/第三方依赖与许可证清单.md`、`THIRD_PARTY_NOTICES.md` 与 `scripts/check_third_party.py`。
- 构建、测试、编码规范与未决问题清单同步引用；D19 记录本次决策。
- 依赖变更流程变为“先登记、后引入”，CI 对未登记引用直接失败。
- 运行库仍保持零第三方依赖，不改变现有安装与消费方式。
- 若未来确需运行期第三方库，必须先新增 ADR 取代本 ADR 第 1 条，再修改构建与分发声明。
