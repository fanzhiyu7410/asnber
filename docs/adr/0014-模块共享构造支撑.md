# ADR-0014：模块共享构造支撑层

- 状态：**已恢复并扩展**（2026-11-10，P1 恢复；P2 大数 INTEGER、P3 X.509 原语、P5 隐式 BIT STRING、P6 零新增原语）
- 日期：2026-11-09；修订 2026-11-10
- 关联：[ADR-0009](0009-分层与独立模块策略.md)、[ADR-0012](0012-标准模块路线与只读边界.md)、[总体架构](../01-架构设计.md)、[编码规范](../08-编码规范.md)、[里程碑与分期](../09-里程碑与分期.md)
- 取代者：无；本 ADR 自身改写（不新增 ADR，避免同一主题出现两条方向相反的记录）

## 修订历史

### 0.4.0：撤回（2026-11-09）

**结论：撤回“模块共享构造支撑层”，设施收回 `asnber-cms` 内部。**

该结论在 P1 之前成立，其事实前提是“只有 CMS 一个消费者”。P1 起该前提失效，
撤回随之撤销，见下节“P1 恢复决策”。本节保留作历史记录。

原因：

1. **只有单消费者**。仓库内对 `module_builder_support.h` 的唯一包含点是 `modules/cms/src/detail/cms_builder_internal.h`；`asnber-pkix` 与 `asnber-pkcs1/8/10/12` 全部只读、没有 builder，从未使用该层。一个使用者的“共享层”只是多一层目录与一条 include 路径，属于多余间接层。
2. **跨模块例外不再有收益**。为单消费者保留“`detail/` 可被任一模块包含”的例外，等于用一条跨子系统规则换取零复用，违反最小约束原则。
3. **收益不变**。原决策要保护的口径统一（单 TLV 校验、形状规则、构树、描述表加载不复制）在 CMS 内部依然成立，只是共享范围收敛到同一模块的多个翻译单元。

落地方式：

- 头文件原样移动到 `modules/cms/src/detail/module_builder_support.h`，`#include "detail/module_builder_support.h"` 调用点不变（`asnber_apply_module_settings` 的 PRIVATE include 已含 `${module_dir}/src`）。
- 删除 `modules/common` 目录与 `cmake/AsnberModule.cmake` 中的 `modules/common/src` PRIVATE include。
- 保留原有可见性约束：header-only、`inline`、不安装、不导出、不进符号表。

原决策中仍然有效的部分：写侧只用核心公共 ABI；构造支撑不包含模块头、描述表或句柄；不形成模块之间的链接依赖。

### P1：恢复（2026-11-10）

**结论：恢复“模块共享构造支撑层”。**

撤回理由“只有单消费者”已失效：P1 起 CMS 之外新增 `asnber-pkcs8` 的
`PrivateKeyInfo` builder，后续 `asnber-pkcs1/10/12` 与 `asnber-pkix` 按同一模式
引用。当前及已排期消费者共 5 个（cms、pkcs1/8/10/12，后续 pkix），
共用内容从“目录间接层”变成真实的校验口径统一需求。

恢复后的形态（相对 0.4.0 原方案的具体化）：

1. **位置**：`modules/common/src/detail/module_builder_support.h`；`modules/common`
   是不产库的源码级目录，不属于 7 个发布包。
2. **接入方式**：`modules/common` 定义 INTERFACE 目标 `asnber_module_support`
   （别名 `asnber::module_support`），include 目录用
   `$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/src>` 声明；
   `asnber_apply_module_settings` 以
   `target_link_libraries(<target> PRIVATE $<BUILD_INTERFACE:asnber::module_support>)`
   接入。`BUILD_INTERFACE` 保证静态库的私有依赖不会以 `LINK_ONLY` 形式
   污染 `install(EXPORT)`。
3. **可见性**：header-only、全部 `inline`、命名空间 `asnber::module_detail`；
   不安装、不导出、不进 `abi/*.symbols.txt`，动态库导出集为 0。
4. **两层设计**：共享层只放领域无关的编码原语（单 TLV 校验、OID 校验、
   `AlgorithmIdentifier` 追加、描述表加载、字节切片与动态数组）；各模块保留
   自己的 builder 句柄、条目结构、OID 常量、形状规则与最终结构编码。
   CMS 的 `using` 声明与薄封装不变，因此迁移前后行为逐字节一致。
5. **排序边界**：DER `SET`/`SET OF` 排序由核心 schema 感知编码负责；共享层
   **不实现**任何排序，只做 `[n] IMPLICIT` 的标签改写
   （`validateAndRewriteSet` 原样迁移）。

验证口径：CMS 迁移后 `ctest` 46/46，六个容器 builder 产物逐字节不变；
PKCS#8 增加 builder 用例后 47/47。

### P2：补充大数原语（2026-11-10）

**结论：任意长度无符号 INTEGER 的编码原语（`createBigIntegerNode`）同样放在共享层。**

PKCS#1 公/私钥 builder 需要同一套“大端无符号幅值 → 规范 DER INTEGER”的规整
规则（去冗余前导零、最高位为 1 时补前导 `00`、零值编码为单字节 `00`、空输入
拒绝）。若只在 `asnber-pkcs1` 内实现，后续 PKCS#8 私钥承载与 PKIX 公钥结构会再
复制一份，符号位与长度处理容易分叉。该原语只依赖核心公共 C ABI 的节点内容
接口，不含领域知识，符合“只收领域无关构造动作”的边界；仍保持 header-only、
`inline`、不安装、不导出、0 符号。上限 `kMaxBigIntegerBytes = 8192` 与错误码
映射（`ASNBER_E_INVALID_ARG` / `ASNBER_E_INPUT_LIMIT`）属于该原语的公共约定。

验证口径：P2 完成时 `ctest` 48/48，`asnber-pkcs1` 符号 15 → 31，表体仍 51,512。

### P3：补充 X.509 编码原语（2026-11-10）

**结论：PKCS#10 与 PKIX 共用的 Name/RDN、证书侧时间、BIT STRING 编码规则放在共享层。**

P3 新增 `modules/common/src/detail/x509_primitives.h`，提供
`selectNameStringTag` / `createNameValueNode` / `createNameNode`、
`createTimeNode`、`createBitStringNode` 与内部辅助 `createTlvAnyNode`。
这些动作横跨 `asnber-pkcs10`（subject、attributes 里的 Name）与 `asnber-pkix`
（issuer/subject、有效期、签名 BIT STRING），若各模块复制，字符串类型选择
（OpenSSL 实测：C/serialNumber/dnQualifier → PrintableString，
DC/emailAddress → IA5String，其余 UTF8String）、UTCTime 边界（1950..2049）
与未用位校验会分叉。

边界调整：共享层除“领域无关构造动作”外，也接收**跨模块共用的 X.509 编码
规则**；仍不放入模块头、builder 句柄、具体结构形状与描述表，仍 header-only、
`inline`、不安装、不导出、0 符号。RDN `SET OF` 排序继续交给核心 DER 编码，
共享层只按调用方顺序建树。

验证口径：P3 完成时 `ctest` 49/49；七包符号不变（69/11/31/22/14/25/148）；
Name 与 OpenSSL 输出逐字节对拍，时间与 BIT STRING 边界用例全绿。

### P4：PKCS#10 复用（2026-11-10）

**结论：不新增原语，`asnber-pkcs10` 的 `CertificationRequest` builder 直接复用
P1–P3 成果。**

`CertificationRequestInfo` 的 `subject` 用 `createNameNode`，`subjectPKInfo`
用 `addAlgorithmIdentifier` + `createBitStringNode`，`attributes` 用
`createTlvAnyNode` 与 `validateSingleDer`。验证口径：P4 完成时 `ctest` 50/50，
`asnber-pkcs10` 符号 14 → 25，表体仍 51,512。

### P5：补充隐式 BIT STRING 与时间校验拆分（2026-11-10）

**结论：共享层增加 `createImplicitBitStringNode`，并把时间结构校验拆成
不依赖文档的 `validateTime`。**

`Certificate` 的 `issuerUniqueID [1] IMPLICIT` / `subjectUniqueID [2] IMPLICIT`
不能复用 UNIVERSAL 标签的 `createBitStringNode`；若在 `asnber-pkix` 内另写一段
标签改写，未用位与填充位校验会与共享层分叉。因此把原实现抽成
`createBitStringNodeImpl`，由 `createBitStringNode`（UNIVERSAL）与
`createImplicitBitStringNode`（CONTEXT）两个薄封装调用。同时 `validateTime`
改为不依赖文档，供 builder 在 `set_*` 阶段提前拒绝非法时间，`createTimeNode`
复用同一校验。仍 header-only、`inline`、不安装、不导出、0 符号。

验证口径：P5 完成时 `ctest` 51/51，`asnber-pkix` 符号 11 → 29，
RSA 自签证书 865 字节逐字节重建，表体仍 51,512。

### P6：PKCS#12 复用（2026-11-10）

**结论：不新增原语，`asnber-pkcs12` 的 `PFX` / `AuthenticatedSafe` builder 直接复用
P1–P5 成果。**

`ContentInfo` 的 `content [0] EXPLICIT` 由模块先用独立文档编出整段包装 TLV，
再以 `asnber_node_create_any` 挂到 `ContentInfo` 下；`data` 形态的包装内是
`createOctetStringNode`，`encryptedData` 形态内是调用方给出的原始 TLV。
`MacData` 用 `addAlgorithmIdentifier` 与共享层的大整数字段写法，
`iterations = 1` 依赖 schema 的 DEFAULT 省略。仍 header-only、`inline`、
不安装、不导出、0 符号。

验证口径：P6 完成时 `ctest` 52/52，`asnber-pkcs12` 符号 25 → 37，
明文与加密两份 OpenSSL PFX 夹具由 builder 重建后逐字节一致，表体仍 51,512。

## 背景

`asnber-cms` 的五个 builder（SignedData / EnvelopedData / EncryptedData / CompressedData / AuthenticatedData）共用同一套构造动作：单 TLV 规范 DER 校验、子节点形状规则、基础构树、描述表加载、字节切片与动态数组管理。实现集中在 `modules/cms/src/detail/cms_builder_internal.h` 与 `cms_builder_common.cpp`。

这些动作只依赖核心公共 C ABI，不含 CMS 结构定义。后续 `asnber-pkix` 与 `asnber-pkcs` 的 builder 需要同一能力；若各模块复制，会让校验口径与错误码行为逐渐分叉，也会让“写侧只产出可担保子集”的边界难以统一维护。P0 决策要求公共设施抽成公共代码，而不是各模块复制。

## 决策

### 1. 新增源码级共享支撑层

- 位置：`modules/common/src/detail/module_builder_support.h`，纯内部目录，不构成独立包。
- 形态：header-only，全部函数 `inline`，命名空间 `asnber::module_detail`。
- 只依赖核心公共 C ABI（`<asnber/asnber.h>`），不包含任何模块头、描述表或句柄定义。
- 通过 `asnber_apply_module_settings` 链接 INTERFACE 目标 `asnber::module_support` 获得
  include 路径；该目标不产库、不导出，模块的链接关系不变，仍然只链核心。

### 2. 只收领域无关的构造动作与跨模块共用编码规则

放入共享层：字节切片、容量管理、单 TLV 校验、OID 校验、SET OF 属性校验与标签改写、子节点形状规则匹配、构树辅助、`AlgorithmIdentifier` 追加、描述表加载（只接受表字节与长度），以及 P3 起跨 `asnber-pkcs10`/`asnber-pkix` 共用的 Name/RDN、证书侧时间与 BIT STRING 编码规则。

留在模块内：builder 句柄结构、条目结构、OID 常量、具体形状规则、条目释放、`ContentInfo` 编码。CMS 侧通过逐名 `using` 声明引入共享设施，五个 builder 的调用点不改；`loadTable` 由 CMS 内的 `inline` 薄封装保持原签名。

### 3. 可见性与安装边界

- 不进入公共头、不进入安装产物、不进入 `abi/*.symbols.txt`。
- 不导出动态符号：函数 `inline` 且带隐藏可见性；命名不带 `asnber_` 前缀。
- 不形成模块之间的链接依赖：共享层是源码级设施，不是 `asnber-cms → asnber-pkix` 之类的包依赖（不改变 ADR-0012 的模块独立结论）。

### 4. 读侧不在本决策内

CMS 与 PKCS 的 `openStructure` 等只读骨架目前各有一份，属于另一项工作；本决策只覆盖构造侧。读侧合并需要单独评估句柄基类与表视图的差异。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 新建内部静态库 `asnber_module_support` | 静态模块的导出集会把私有依赖记入 `INTERFACE_LINK_LIBRARIES`，需要额外 `$<BUILD_INTERFACE:...>` 才不污染安装导出；全静态消费者同时链接多个模块时，同名外部符号有重复定义风险；收益仅是减少少量重复编译。P1 采用 **INTERFACE** 目标（不产库、不编译），只借它传 include 路径，规避上述两个问题 |
| 放进核心 `src/internal/` 的内部目标 | 共享库在隐藏可见性下不导出这些符号，模块无法在 DLL 边界上使用；导出则改动 ABI；且 `AlgorithmIdentifier` 等领域词汇进入核心，违反 ADR-0009“核心零领域” |
| 各模块复制一份 | 正是 P0 决策要消除的做法；校验口径与错误码会分叉 |
| 顺带合并读侧骨架 | 读侧涉及句柄基类与表视图差异，改动面更大，混在一起无法用“行为逐字节不变”验证 |

## 后果

- 分层增加一个“模块共享支撑层”：允许依赖核心公共 ABI，禁止进入安装产物、公共头、符号表，禁止放置描述表与句柄。
- `docs/08` 对 `detail/` 的“只允许同一子系统包含”规则增加一条明确例外。
- 后续 PKIX/PKCS builder 直接复用该层，不再复制校验与构树代码。
- 验证口径：重构前后 `refactor_baseline.py --strict` 输出逐行一致，7 个库的导出表
  逐符号一致，断言数与描述表不变（P1 实测 46/46 → 47/47，pkcs8 15 → 22 符号）。
