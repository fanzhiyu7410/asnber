# ADR-0009：分层与独立模块策略

- 状态：已确认（用户批准，2026-11-03；决策 6 由 [ADR-0012](0012-标准模块路线与只读边界.md) 修订）
- 日期：2026-11-03
- 关联：[总体架构](../01-架构设计.md)、[C API 规范](../02-C-API规范.md)、[能力范围](../03-ASN1能力范围.md)、[构建与移植](../06-构建与移植.md)、[里程碑](../09-里程碑与分期.md)、[ADR-0002](0002-编码规则范围.md)、[ADR-0003](0003-值表示模型.md)、[ADR-0007](0007-模式层边界.md)、[ADR-0012](0012-标准模块路线与只读边界.md)

## 背景

项目最初按通用 ASN.1 库设计，随后一度把 PKIX 结构直接内嵌到核心库。该做法会让核心带上证书、密钥、签名算法等领域概念，破坏通用性，也使 CMS/PKCS 等后续模块无法独立演进。

用户最终确认分层：核心库只做通用 ASN.1 编解码、DOM、内存与错误模型、模板机制；标准结构以独立包的上层模块提供。模板机制是核心能力，不是二期可选项。

## 决策

1. **核心零领域知识**：`asnber` 核心中不得出现 X.509、PKIX、CMS、PKCS、证书、密钥、签名算法等领域概念，不得内置标准结构表。核心只处理标签、节点、文档、值、模板描述与编解码。
2. **独立模块**：标准结构放在独立 CMake 包，各自有版本、导出配置与公共头文件。
   - `asnber-pkix`：RFC 5912 的 PKIX1Explicit-2009 / PKIX1Implicit-2009 / PKIX-CommonTypes-2009；来源、勘误与更新链见[描述表格式](../11-描述表格式.md)第 15 节。
   - `asnber-cms`：RFC 6268；第一版只读 `ContentInfo`/`SignedData` 结构（0.2.0 第一块起追加 `EnvelopedData` 只读）。
   - `asnber-pkcs`：RFC 8017（PKCS#1）、RFC 5208（PKCS#8）、RFC 2986（PKCS#10）、RFC 7292（PKCS#12）；第一版只读结构。执行顺序与切片见 [ADR-0012](0012-标准模块路线与只读边界.md)。
3. **依赖方向单向**：模块 → 核心；核心不得引用任何模块。模块之间基线期不互相依赖。
4. **模板机制在核心**：类型描述以“已编译描述表”形式进入核心，可为 C 源数组或二进制资源；核心运行期不解析 `.asn1` 文本，避免把语法解析器塞进核心。
5. **两条入口等价**：运行时注册 C API 与描述表加载都构建同一棵 `Schema` / `TypeDescriptor` 类型树，字段命名、约束校验、`CHOICE`/`SET OF`/`OPTIONAL`/`DEFAULT` 判定使用同一套语义。
6. **工具边界**：`.asn1` 文本解析、语义校验、描述表生成放在独立工具 `asnberc`。一期交付 MVP（解析文本 → 生成描述表）；输入支持**自包含展平模块**与多模块 `IMPORTS`（A 阶段落地，单表合并，9007 已移除），参数化仅报 9006；`CLASS`/`WITH SYNTAX`/信息对象集以预展开模块输入；参数化展开与直接解析原始 RFC 模块留后续。工具不进入核心 ABI，核心不链接工具。（本条由 [ADR-0012](0012-标准模块路线与只读边界.md) 修订。）
7. **一期验证消费者**：`asnber-pkix` 是模板机制的首个消费者；一期必须能解析真实 X.509 证书并取到 subject/issuer/validity/extensions。
8. **值类型能力在核心**：大整数只读视图/十进制导出、UTCTime/GeneralizedTime 结构化只读解析属于核心通用值类型能力，一期交付；不做大整数运算，不做时区归一。
9. **多包与版本**：同一仓库多包；核心 `asnber` 与 `asnber-pkix`/`asnber-cms`/`asnber-pkcs` 各自安装导出到 `lib/cmake/<pkg>`。模块包 `find_package` 时自动依赖核心；核心 ABI 稳定期内模块可独立升级。
10. **编码规则收敛**：一期 BER 解码 / DER 编解码；CER 需求触发；PER/UPER 暂不规划，重启条件为出现明确 PER 场景需求。
11. **验证边界**：本库只做 ASN.1 编解码与结构校验，不做签名验证、证书链构建、有效期策略或吊销检查。

## 模板表格式与工具边界

- 描述表是一份带 `format_version` 的已编译数据，包含模块默认标注方式、字符串池、类型表、字段表、约束表与默认值表；类型构造性由 `kind` 派生，DEFAULT 以规范 DER TLV 存放。布局已冻结为 `uint8_t[]` 显式小端读取，不依赖 C 结构体布局，见[描述表格式](../11-描述表格式.md)。
- C 源数组与二进制资源指向同一份逻辑格式；核心加载器只做结构校验与类型树构建，不做文本语法解析。
- `asnberc` 是唯一解析 `.asn1` 文本的组件；它输出描述表，供模块构建或宿主集成使用。
- 标准模块的描述表由 `asnberc` 从公开 RFC 模块生成，随模块发布；不得手写维护第二份结构定义。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 核心内置标准结构（PKIX/CMS/PKCS） | 核心被领域概念污染，模块无法独立演进，通用用户被迫承担体积与依赖 |
| 外部描述文件（自定义 JSON/二进制 DSL） | 与公开 RFC 模块形成双份事实来源，易漂移，且新增私有格式维护负担 |
| 代码生成强类型结构体 | 破坏 C ABI 稳定、跨语言与不透明句柄约束，模块版本难以独立 |
| 把 `.asn1` 解析器嵌入核心 | 核心体积与依赖膨胀，嵌入式无法裁剪，违背核心零领域/零文本解析原则 |
| 模板机制推迟到二期 | `asnber-pkix` 一期无法落地，证书字段名与约束校验无法验收 |
| 模块与核心同包同版本 | 任一模块升级会强迫核心与其他模块同步发版，违背独立演进目标 |

## 后果

- 核心公共头文件、目录与文档不得出现领域词；模块头文件使用独立前缀与包名。
- 一期必须同时交付核心模板机制、`asnberc` MVP 与 `asnber-pkix`；三者缺一不可验收。
- 模块安装导出必须声明对 `asnber` 的依赖，并保留各自版本号。
- 后续新增标准结构先新增独立模块与 RFC 编号，不得回填进核心。
- PER/UPER 重启前必须修订本 ADR 与 [ADR-0002](0002-编码规则范围.md)。
