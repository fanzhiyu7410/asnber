# 发版说明规范

本规范约束 GitHub Release 正文的写法。目标是让每个版本的说明结构一致、读者一致：发版说明回答“我升级后会多什么、少什么、要改什么”，不是内部验收报告。

## 1. 目的与读者

- 读者是**使用者**：下游集成方、调用方、需要评估升级成本的人。
- 发版说明只回答四类问题：新增了什么、变化了什么、修复了什么、升级要注意什么。
- CI 与测试是发版的**前提**，不是发版的内容：它们决定“能不能发”，不在正文里交代。

## 2. 载体、标题与分工

| 载体 | 定位 | 允许的内容 |
| --- | --- | --- |
| `CHANGELOG.md` | 仓库内的开发记录 | 按版本累积的完整变更，可含模块、符号、描述表等实现层信息 |
| GitHub Release 正文 | 面向使用者的摘要 | 使用者可感知的变化，以及升级后果 |

- Release 标题只用版本号（如 `v0.3.0`），与 tag 同名，不加产品名前缀。
- 两者不互相复制：Release 不搬运 CHANGELOG 的条目清单；CHANGELOG 不为了发版改写成宣传语。
- 判断某条内容放哪：**使用者是否需要据此改代码、改构建或做取舍**。需要，进 Release；只是内部实现事实，留 CHANGELOG 或不写。

## 3. 固定结构

正文以 2–3 句概述开头（不设标题），随后按下列固定顺序使用小节。没有内容的小节整节省略，不写“无”。

1. **新增**：新能力、新 API、新公共头、新包。
2. **变更**：既有行为、语义、默认值、头文件组织、包结构的变化。
3. **移除**：删除或废弃的 API、选项、平台支持，并给出替代方案。
4. **修复**：使用者可能已经遇到的缺陷，以及修复后的结果。
5. **升级注意**：升级必须做的动作，包括 ABI/源码兼容性、需要更新的基线或配置、同一 API 跨版本的语义差异。
6. **已知边界**：本版明确不做什么、哪些结论不成立、哪些判断仍由调用方自行完成。

顺序理由：先讲“能多做什么”，再讲“变了什么、少了什么”“修了什么”，最后集中放“升级动作”和“边界”，让只需要评估升级的人只读后两节。

## 4. 每个小节怎么写

- 写**影响与后果**，不写实现路径。例：“`open` 只接受裸结构，外层 `ContentInfo` 需先剥离”，而不是“新增 7 个导出函数、内部复用某模块”。
- 每条说清三件事：发生了什么、对调用方意味着什么、需要做什么。说不清第三点的条目通常不该出现在 Release。
- 同类改动合并为一条，不按文件、提交或 PR 罗列。
- 仅在构成契约时给数字（SO 主版本、包版本区间、长度上限、超时默认值）；统计类数字不写。
- API、类型、字段名用反引号，措辞与公共头一致。
- 用陈述句；不使用“重大升级”“性能飞跃”这类无信息量的修饰。

## 5. 禁止项

Release 正文不得出现：

- CI run ID、workflow 名称与 job 数量、结论链接；
- 测试通过数（如 `40/40`）、断言点数量、覆盖率、差分样本数；
- 构建耗时、机器配置、一次性性能微基准（除非该版本以性能为主题，且给出可复现口径）；
- 内部提交 hash、分支名、tag 对象、评审过程与结论；
- 过程性证据：`regen=equal`、`BASELINE OK`、日志路径、临时构建目录；
- 纯内部重构流水账：不改变行为、公共头与产物的重构不单独成条；确有影响的并入“变更”一句话。

## 6. 长度与详略

- 单个版本建议 400–1200 字。明显更长通常意味着把 CHANGELOG 搬了过来。
- 每个小节 1–6 条，每条 1–3 句；条目过多时按使用者场景合并。
- 保留“读者需要据此行动”的信息；删掉后不影响理解的段落一律删。

## 7. 模板

```markdown
（2–3 句概述：本版主题、覆盖范围、是否存在破坏性变更）

## 新增

- …

## 变更

- …

## 移除

- …

## 修复

- …

## 升级注意

- …

## 已知边界

- …
```

没有内容的小节整节删除；“移除”常用于确实删除了 API 或平台支持的版本。

## 8. 生效范围

本规范自首个版本 0.1.0 起执行。
